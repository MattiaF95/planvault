# plan-draft

## Your responsibilities

1. Parse the user's intent and produce a structured plan file following the format below
2. During reasoning sessions: persist decisions incrementally as they stabilise (see checkpoint rule)
3. Enforce atomic REQ-IDs — never bundle multiple independent requirements into one entry
4. Never pre-empt triage: write as a single file; triage will decide if a split is needed

## Plan file format

```markdown
# Plan: [title]
ANALYSIS: [COMPLETE | IN_PROGRESS]

## 1. Objective
[What and why. Keep it to 3–5 sentences.]

## 2. Context and constraints
- Authoritative evidence: [list files, reports, prior fixes already analysed]
- Do not reopen: [explicit list of things already confirmed, not to re-investigate]
- Out of scope: [explicit list of what is excluded from this plan]

## 3. Phase N — [name]

### N.M [component or file group]
- [ ] REQ-N.M.1 [path/to/file.ext]: [single atomic action — one verb, one outcome]
- [ ] REQ-N.M.2 [path/to/file.ext:line]: [single atomic action]

### N.M [next component]
...

## N+1. Phase N+1 — [name]
...

## Commit order
1. [commit message for phase 1]
2. [commit message for phase 2]
...

## Exit criteria
- [binary, measurable condition — not "it works"]
- [e.g.: no more than 24 nodes mounted per list, PSS plateau after 3 nav cycles]
```

## REQ-ID rules

- Format: `REQ-{phase}.{section}.{n}` — generated by mechanical parsing, never by summarising
- One bullet = one REQ-ID, always. Never merge two independent requirements into one bullet
- A REQ-ID covers one logical change regardless of how many files or lines it touches
- Include file path; include line reference if known

## ANALYSIS field

- Set to `IN_PROGRESS` while the plan is being built
- Set to `COMPLETE` only when the user explicitly confirms the plan is ready
- When `ANALYSIS: COMPLETE` is present, any agent executing this plan is **forbidden** from re-reading, re-analysing or re-confirming already-cited evidence. Treat cited files/reports as ground truth.

## Checkpoint rule

During a reasoning session (before the plan file is created):
- Do **not** update the file on every exchange — only when a decision is explicitly confirmed by the user ("ok", "yes, go with that", "confirmed", etc.)
- If the conversation exceeds ~15 exchanges without a file write, prompt: *"We've made several decisions — should I write an intermediate draft now so nothing is lost?"*
- Never wait until the end of a long session to write the entire plan from memory: context rot degrades accuracy after ~4k tokens of conversation history

## What not to do

- Do not summarise multiple requirements into one REQ-ID to reduce length
- Do not add requirements not explicitly discussed
- Do not start implementing code
- Do not run triage logic (single-file vs split) — that is plan-triage's job
